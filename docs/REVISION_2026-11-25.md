# 研究修订说明（2026-11-25）

历史脚本、ep10 数字和原始结果目录都保留。这一版只加了可单测的口径、复核图、checkpoint 身份和新的 Colab 入口。没有重训，没有改 `modal_stage_*.py`。

## 指标

`modal_stage_e_cont2.py` 的 `eval_rows`（以及更早的 stage B–E）在 argmax 之后用 `pred != 0` 对二值 GT 算 Dice / IoU。`by_class` 只是按帧标签把这个 binary 分数再平均。`pred_name` 取前景里面积最大的类。所以前景 Dice 高，不表示类别画对了。

新代码在 `revision/metrics.py` 里把三件事分开：

- `binary_foreground_dice` / `binary_foreground_iou`
- 真正的 class-aware：每类像素 Dice / IoU，像素池化 macro，以及患者等权 macro
- 命名 accuracy、macro F1。命名仍然是最大面积类别，不能代替 class-aware Dice

帧等权和患者等权都给出。配对不确定性用患者簇 bootstrap，两组使用同一次患者抽样。

只有标量 `mean_dice` 时，能恢复的只是「帧等权 binary foreground」。`by_class` 同样不是像素级类别 Dice。逐帧历史 JSON 若带 `dice`、`pred_name`、`cls`、`patient`，可以重算 binary、命名和患者加权，以及这些已存分数的 bootstrap。像素级 class-aware Dice、mIoU 和 TP/FP/FN 图恢复不了，也不会用 binary 分数去填。

`clean22` 不是新的独立测试集。它是 `old100` 里患者不在新训练集中的子集（`split_summary.json`：old100 有 100 帧，其中 78 帧落在 train）。历史表格里的 clean22 数字是这个子集上的 binary foreground Dice。

## 用词

冻结骨干、随机初始化后再在 SEA 上训练的 1×1 head 是监督探针，不是 zero-shot。README 里原先的 “0-shot control” 按这个意思撤回；YOLOv11 那段另说的 zero-shot 对比仍然只是历史记录，而且解密未完成。

## 几何和预算

Stage E 及之后的 ep10 是中心正方形裁到边长后再缩到 768×768。Stage B/C/D 是直接拉到 768×432。两组历史数字不能当成同一几何下的比较。

Stage E 的 control 和 fine-tune 预算都写的是最多 6 epoch、patience 2。fine-tune 后来又从 ep5 续到 ep10，control 没有续。因此 ep10 对 control 不是同一训练预算。新的四组配置固定 6 epoch、不早停、不从 ep10 续，有效 batch 8（微批 1、累积 8）。选 checkpoint 沿用 Stage E 当时的规则：本地 val 的帧等权 binary foreground Dice。`gt_class_dice`、class-aware macro Dice 和命名准确率会记下来，不参与选点。独立测试不参与选点。上一版草稿曾把选点改成 GT 类别 Dice，那是静默改协议，已经改回。

`stretch_768x432`、`letterbox_768`、`center_crop_native` 只写在几何表里，不进入这四组。

## 权重身份

最终 control 的逐帧 JSON 在体积上的路径是 `results_e/results_control.json`（本次修订没有把该文件放进 git，也不把它写成缺失）。Drive 里名为 `best_control.pt`、`best_val_dice` 为 0.8682456 的文件是旧 B2 epoch 3 的 stretch head，不是 Stage E control（binary val 0.9394298）。这个标量只产生 `historical_b2_scalar` 警告。身份是调用方在本地记录的 sha256、架构字段，以及 `control_head`（只有 head）还是 `full_finetune`（含 backbone）。仓库不要求事先存有私有文件的哈希才允许配置。文件名不参与认定。

新运行目录必须以 `fairrun-` 或 `smoke-` 开头，已存在就拒绝覆盖，路径里也不许出现 `results_*` 或 `viz_*`。`RUN_RECORD.json` 记下 git 修订、`revision/` 源码哈希，以及调用方传来的 manifest / checkpoint 哈希。

## 四条骨干

两边都按 ViT-B/16、深度 12、embed 768、约 86M 来配 head。InnerLogic-Surg 是 DINOv3 格式的手术持续预训练（GitHub `semaphor-surgical/Innerlogic-Surg` Release v0.1.0，文件名 `dinov3_vitb16_pretrain_innerlogic_surg-a516a775.pth`，仓库里已有的 sha256 前缀与文件名一致）。代码和权重沿用 DINOv3 License。通用对照是 Hugging Face `facebook/dinov3-vitb16-pretrain-lvd1689m`（LVD-1689M，同样是 DINOv3 License，需要先接受许可）。本次没有下载通用权重，也没有核到可以钉死的 sha256，因此该配置在校验和写入之前拒绝加载，并且拒绝用 InnerLogic 文件顶替。ViT-L（`22622135`，embed 1024）不在这四组里。上游 README 的 checkpoint 表目前列的是 ViT-B/16 和 ViT-L/16；论文写 ViT-S/16 会一并放出，不能用别的规格代替。

通用 DINOv3 的下载和许可证门控仍写在 `revision/pretrain.py` 的获取步骤里。没有 `expected_sha` 时真实加载会拒绝，也不能用 InnerLogic 文件顶替。这个缺口不挡住训练逻辑：`revision/engine.py` 的 `TinyDino` 只实现同样的 `get_intermediate_layers` 接口，用合成小图在 CPU 上跑冻结、末 4 block、梯度累积、binary 选点、断点（optimizer / scheduler / RNG）和一轮推理。它不是 ViT-B/16。

真实入口是 `launch_real`。它要求本地权重路径、调用方自己记录的 sha256、数据根和 jsonl manifest，再用 `surgfm_probe.load_backbone` 实例化。缺文件、目录不可写、磁盘不足、指定了 cuda 但没有 bf16，都会立刻报错。默认 device 是 cpu，即使机器有 GPU 也不会自动占用。CUDA 路径只用 bf16，不用 fp16。本修订没有在 Colab 或 GPU 上跑过真实训练。

## Colab
